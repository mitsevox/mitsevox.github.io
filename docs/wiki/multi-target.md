# Multiple targets

Activating a second original safely, sharing one source tree between targets, carrying a map from one to the next, validating a change on every target, and the life of a target from listed to archived.

A target is one original binary ([Targets](/wiki/targets/)). Everything in this guide is laid out for several targets from the first commit, so a second disc revision, region or platform adds a target and changes no file's shape. This chapter is the procedure for doing that, written so that it can be followed step by step with a pass or fail gate after each step. It is a procedure, not a validated one: nothing in it is validated end to end until two real targets of one repository have passed every gate. The kit's tools for it are tested on disposable fixtures only, and the chapter says so where it matters.

## What is shared and what is per target

| Per target (`config/<id>/`, `orig/<id>/`, `build/<id>/`) | Shared (one copy) |
| --- | --- |
| The toolkit inputs (`config.yml`, `splits.txt`, `symbols.txt`), `build.sha1`, `evidence.tsv`, `README.md`, a linker script template, tool reports | `src/`, `include/`, `configure.py` (the union of units, with `MatchingFor` where a unit links on some targets only), `tools/`, `tests/`, `docs/`, `references/`, the three JSON files under `config/` |
| The original in the private image at `/orig/<id>/...` and the data directory `data/<slug>/<id>/` | The build image (one image holds every original), `validate.yml`, the site page |

A unit that exists on some targets only is absent from the other targets' `splits.txt`. A function present on one target only is an `#if VERSION_<ID>` block in the shared file. Nothing is copied between targets and nothing is inherited: each target's own objdiff report scores it ([Build, verify, measure](/wiki/build-verify-measure/)).

## Activating a second target

The target is `GAME01-rev1` below; `GAME01-rev0` is the target active so far. Each step ends with a gate; a failed gate means stop, report what was seen, and change nothing to get past it.

1. **List it.** `config/targets.json` lists `GAME01-rev1` as `planned` (or `archived`, when it was listed and set aside earlier) with the original's SHA-1, and `config/GAME01-rev1/README.md` and `orig/GAME01-rev1/.gitkeep` exist. Gate: `python3 tools/targets.py check` passes and `python3 tools/versions.py check` passes.
2. **The original into the image** (owner). Commit the original to the private repository under `orig/GAME01-rev1/`, add its `COPY` and `sha1sum -c` lines to the Dockerfile and its line to the image workflow's verification, merge, and take the new digest from the run summary ([Build environment](/wiki/build-environment/)). Gate: the image workflow is green on `main` and its summary prints `ghcr.io/owner/game-build@sha256:<64 hex digits>`.
3. **Scaffold.** `python3 tools/new_target.py GAME01-rev1` writes `config/GAME01-rev1/config.yml` and an empty `evidence.tsv`, and adopts the README placeholder and the `.gitkeep` that are already there. Gate: the tool prints `wrote` for `config.yml` and `evidence.tsv` and `adopted` for `README.md` and `.gitkeep`; a `refusing to overwrite` line means the directory holds real content and the procedure stops.
4. **Pin the scope of every unit.** `python3 tools/matching_scope.py pin GAME01-rev0` rewrites every unconditional `Matching` in `configure.py` to `MatchingFor("GAME01-rev0")`: the new target inherits no claim, and on it every unit is `NonMatching` until proven. Gate, in two parts: the tool prints `pinned N Matching declaration(s)` (a `Matching is used outside` line means a hand edit is needed first), and the existing target is unchanged: `python3 configure.py --version GAME01-rev0` before and after the rewrite produces identical `build/GAME01-rev0/build.ninja` and `build/GAME01-rev0/objdiff.json` (`cmp` reports no difference), and `ninja -f build/GAME01-rev0/build.ninja` still ends with its `main.dol: OK`.
5. **The first split.** With your own copy of the new original at `orig/GAME01-rev1/<original path>`, produce the first `symbols.txt` and `splits.txt` with the toolkit's analysis, the way the project's first target was bootstrapped (the project's README says how), then `python3 configure.py --version GAME01-rev1` and `ninja -f build/GAME01-rev1/build.ninja`. Every unit is `NonMatching` on this target, so the link is the original's own objects relinked. Gate: the build ends with `build/GAME01-rev1/main.dol: OK`; `config/GAME01-rev1/build.sha1` holds the registry's SHA-1 for the target; `python3 tools/matching_scope.py show` lists no unit as `all`; the measurement `ninja -f build/GAME01-rev1/build.ninja progress build/GAME01-rev1/report.json` writes a report in which `linked` is 0 for code and data.
6. **Activate.** Set `status: active` in `config/targets.json` (the default target stays what it was), point `validate.yml`'s `BUILD_IMAGE` at the new digest, and open the pull request. CI builds both targets, because `configure.py` and `config/targets.json` are shared paths. Gate: `Validate GAME01-rev0` and `Validate GAME01-rev1` are both green, including `Check the report` for each, and `Validate targets` passes; the scaffold check prints no warning about the new target's files.
7. **Publish.** Merge (owner). Gate: the first `main` run's `Validate GAME01-rev1` job prints `published <slug>/GAME01-rev1 <sha>`; `data/<slug>/GAME01-rev1/latest.json` exists in the data repository with `linked` 0; the game page shows the target in the picker with its own measurement; the existing target's numbers are unchanged.
8. **Widen.** From here every shared unit counts on the new target as soon as its `splits.txt` names the unit, `configure.py` says `Matching` or `MatchingFor` for it there, and its `symbols.txt` gives the functions the same names; that is the map transfer below.

Steps 1, 3, 4, 5 and 6 are an agent's; steps 2 and 7 are the owner's.

## Shared source with two targets and with more

The convention is in [Build, verify, measure](/wiki/build-verify-measure/): one define per target, differences under `#if VERSION_<ID>` in the shared file, groups in `include/version.h`, whole-function variants when a function would carry three or more blocks or more than about a third of its lines inside blocks. Three things change when the third target is listed:

- **Conditions name their targets.** `!VERSION_X`, a group that negates a token, and `#else` after a version condition cover every target not named, including one listed later. With two targets they mean the other target and `versions.py check` warns; from the third listed target on they are errors, so the pull request that lists a third target rewrites every such block as `#elif VERSION_Y`, a list `VERSION_Y || VERSION_Z`, or a group. The check runs on `src/`, `include/` and `configure.py`, in `Tool tests` and in the scaffold check.
- **Groups say what the targets share**, not which they are: `REGION_USA`, `PLATFORM_WII`, `REV_LATER`. A group is defined once, in `include/version.h`, as a boolean expression of defines and earlier groups, and a difference shared by two or more targets uses the group rather than listing the ids in every file. `versions.py view --target <id> <file>` shows what one target compiles; a reviewer reads `versions.py diff --target <a> --target <b> <file>` for each pair the change touches.
- **Whole-function variants** stay the exception: one function-level `#if ... #elif ... #endif` per variant, in the same file, when inline blocks would make the function unreadable. Never a `src/<id>/` file for a unit two targets share.

Per-target matching is `Object(MatchingFor("GAME01-rev0"), "unit.cpp")` until a unit links byte-identically on every active target, when it becomes `Matching` again; `python3 tools/matching_scope.py show` lists the state, and the PR's Targets table reports the `Matching` state per target for each touched unit. Promotion on a target is a tier B change for that target; it needs the byte-identical link there, which CI proves.

Compiler and library profiles are per target when the targets were built differently: whole profiles chosen by `config.version` in `configure.py`, never a per-function or per-unit exception, with a `compiler` row in each target's `evidence.tsv` that names the compiler version, the flags and what established them ([Evidence](/wiki/evidence/)). A profile change is tier A: `tools/tier.py` raises the floor for a `cflags`, `ldflags`, `asflags` or `mw_version` line, and the hostile checklist's `Compiler settings` row asks for the evidence at the right scope. The same profile on two targets is one profile with two evidence rows, one per target, because a claim is per target by definition.

## Carrying a map to a new target

A new target starts with the toolkit's own `symbols.txt` and `splits.txt`: tool labels for every function, units where the toolkit found them. The sibling's map carries over function by function, and the result is a set of candidates, never evidence, until the new target's own bytes confirm each one. This section specifies the transfer; the tool that performs it is not built yet, because it needs a second original to be built against, and it is listed below as an unknown.

1. **Anchor.** For every function of the sibling that has a recovered name, find its counterpart in the new original by its body: the same instruction bytes with relocation fields masked, the same size, the same shape of relocations. A sibling function with exactly one counterpart is a unique candidate; one with several is ambiguous; one with none is removed on the new target. A function of the new original that no sibling function reaches is added there.
2. **Propose.** Unique candidates propose the name in the new target's `symbols.txt`, and a unit boundary in its `splits.txt` where every function of a sibling unit maps and the counterparts are contiguous in the new target's address order without interleaving with another unit's. Ambiguous, added and removed functions keep their tool labels and are listed; nothing is guessed from position alone.
3. **Validate.** Boundaries: a proposed unit's counterparts are contiguous and the sections agree (code stays code, data stays data). References: a call or data reference from A to B in the sibling corresponds to a reference from A' to B' in the new original; a mismatch demotes the candidate to ambiguous. The relink of the new target stays byte-identical with every unit `NonMatching`, and `python3 tools/versions.py check` and `python3 tools/targets.py check` pass.
4. **Record.** The tool writes one regenerable report under `config/<new id>/` (every function with its class: unique, ambiguous, added, removed, and the sibling function it maps to) and the candidates go into `symbols.txt` and `splits.txt`, which are toolkit inputs, not claims. The evidence record gets one row per tool run, not one per function: kind `name` and kind `unit-anchor`, origin `related`, the subject naming the tool with its inputs and revision, the evidence the report's path, and `provisional` edges on the `unit` rows it proposes. A claim becomes the new target's own, origin `target` with `exact` edges, only when that target's bytes establish it: the unit links byte-identically there (`MatchingFor` widened to it) or the target's own symbols or debug information name the function.
5. **Review.** The transfer is one tier A pull request for the new target (`splits.txt` and `symbols.txt` change), reviewed against the new target's disassembly, with the report as the evidence and the ambiguous list as the open questions. Its Targets table shows the sibling unchanged.

The tool is `tools/transfer_map.py <from id> <to id>` when it exists. Its tests must include a target transferred onto itself (every function unique, every unit intact) before the real pair; its first real run is part of validating this chapter, and the real unknowns are what that run finds: the address deltas, the functions the compiler laid out differently, and whether the toolkit's analysis of the new original needs the same project patches as the first.

## Validating a change on every target

A shared change is safe for a target only when that target was built with it. The rule and its records are in [Contribution workflow](/wiki/contribution-workflow/); here is how CI and the author divide the work:

- **What CI builds.** The planner builds every active target for a change under a shared path (`src/**`, `include/**`, `configure.py`, `tools/**`, `validate.yml`, the three JSON files; `extern/**` or `tests/**` where the repository lists them) and only the owning target for a change confined to `config/<id>/**` or `orig/<id>/**` ([Targets](/wiki/targets/)). So a pull request that touches `src/` is validated on every target by CI, and a pull request that touches one target's `splits.txt` is validated on that target alone, which is right, because no other target reads that file.
- **The Targets table.** One row per active target: built locally or `CI only`; byte-identical; the units touched with their `Matching` state on that target (`matching_scope.py show`); the progress delta from that target's report (linked, matched, exact functions, before and after); the evidence rows added to that target's file. A row that says `not affected` is only right for a change confined to another target's `config/<id>/`.
- **Regressions.** A unit that linked on a target and no longer does fails that target's build at the hash check; CI catches it before the table. A function that drops from exact without breaking the link is a negative delta in the table and a finding for the reviewer; a reviewer asks why a shared change moved a target it was not meant to touch.
- **Reviewer coverage.** Each record's `Targets:` line names the targets the reviewer checked; a record covering one target never counts for another, and a tier A pull request that changes a shared unit needs its records to name every active target the unit links on. A change to one target's map or profile needs records for that target.

## The life of a target

- **Listed.** `planned` or `archived` in `config/targets.json`, with `config/<id>/README.md` and `orig/<id>/.gitkeep`. Nothing builds it; the page lists it without a measurement.
- **Active.** The steps above. Progress is not a condition: a target at 0 linked is active.
- **Archived.** Set `status: archived`. Its directory, its data directory and its history stay; publishing refuses it (`Target <id> is not an active target`) and the page lists it without a measurement. The default target must stay active, so change `defaultTarget` first when archiving the default. CI no longer builds it, so a shared change is not validated on it; an archived target's `MatchingFor` entries stay as they are, a record of what linked when it was last built.
- **Reactivated.** Set `status: active` again. Its files must still be there (`targets.py check`), the image must still hold its original at the digest `validate.yml` names, and shared changes made while it was archived have not been built on it: the first build after reactivation may fail at the hash check, and every unit it fails on is pinned back to the targets that link it until it is repaired. Its data directory continues where it stopped: the history gains rows from the next publish, and `latest.json` moves forward because the new commit is newer.
- **Default target changed.** Edit `defaultTarget`; the next publish of any active target rewrites `game.json`, the hub card and the page without `?target=` show the new default, and every `?target=<id>` URL still works.
- **A failed or partial publication.** Each target publishes in its own job and its own commit, so one target's failure never holds back another's. The publish is idempotent per revision: re-running the failed job (Actions, the run, re-run failed jobs) publishes the revision if it never reached the data repository, or prints `<slug>/<id> <sha> already published` if it did, and a run of an older commit that finishes late appends its history row without touching `latest.json`. A publish that pushed is complete: the files of a target are written together and committed once. A wrong published file is corrected in the data repository ([Publishing](/wiki/publishing/)), never by re-running the measurement, which keeps what was published first.
- **Histories.** One history per target, from its first publish, never rewritten; a target id is permanent because it names that history. The disc revision (`revision` in `targets.json`, a display string) and the Git revision (`source.revision` in `latest.json`, the measured commit) are different things: a history row is one Git commit measured on one target, and the same commit has one row per active target.

## What has been validated, and what has not

- The three kit tools (`matching_scope.py`, `new_target.py`'s adoption, `versions.py`'s broad-condition rule) are tested on disposable fixtures in `tests/test_targets.py`: a `configure.py` with the plain `Object(Matching, ...)` form, a scratch registry with two and three targets, a placeholder README. Those fixtures are not a second original.
- The activation steps, the transfer specification and the lifecycle have not been run on two real targets of one repository. The first repository to do so validates this chapter, and its pull requests are the record; until then every statement above about what a step shows is what the code does on fixtures, not what a real second target did.
